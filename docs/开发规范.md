# 《竞拍之王》项目开发规范

> 版本：v1.0  
> 适用：`bid-king` Monorepo（客户端 Cocos Creator + 服务端 Node.js/Colyseus + 共享协议包）  
> 技术栈：TypeScript 全栈  
> 原则：**强约定、少争论、工具自动化、1-2 人团队零负担**

---

## 一、总体原则

1. **能被工具检查的规则，一律交给工具**（ESLint / Prettier / TypeScript / husky）。
2. **规则优先级**：工具报错 > 本文档 > 个人习惯。
3. **只约束需要的**：本文档列出的是**强制项**；未列出的按社区主流写法即可，不要过度设计。
4. **Commit 即责任**：每一次提交都要能被别人（或 3 个月后的自己）看懂。
5. **TypeScript 严格模式不可关**，`any` 必须有充分理由 + 注释说明。

## 四、TypeScript 规范

### 4.1 `tsconfig.base.json` 核心配置（强制）

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",
    "module": "ESNext",
    "moduleResolution": "Bundler",
    "strict": true, // 必须开
    "noImplicitAny": true,
    "strictNullChecks": true,
    "noUnusedLocals": true,
    "noUnusedParameters": true,
    "noImplicitReturns": true,
    "noFallthroughCasesInSwitch": true,
    "esModuleInterop": true,
    "forceConsistentCasingInFileNames": true,
    "skipLibCheck": true,
    "resolveJsonModule": true,
  },
}
```

### 4.2 类型使用约定

- **优先 `interface`**，联合类型用 `type`。
- **禁止 `any`**；必须用时加 `// eslint-disable-next-line @typescript-eslint/no-explicit-any` + 理由注释。
- **禁止 `@ts-ignore`**，改用 `@ts-expect-error` 并注明原因。
- **公共 API 必须显式写返回类型**，内部函数可推导。
- **枚举用 `const enum` 或 `as const` 字面量联合**，避免运行时膨胀（特别是客户端包体敏感）。

```ts
// ✅ 推荐：字面量联合
export const RoomState = {
  WAITING: 'WAITING',
  PREVIEW: 'PREVIEW',
  BIDDING: 'BIDDING',
  REVEALING: 'REVEALING',
  SETTLING: 'SETTLING',
  END: 'END',
} as const;
export type RoomStateType = typeof RoomState[keyof typeof RoomState];

// ❌ 避免（除非跨包传输）
export enum RoomState { WAITING, PREVIEW, ... }
```

### 4.3 导入路径

- **包内**使用相对路径，最多到上一级：`../services/userService.ts`。
- **跨包**使用包名：`import { RoomState } from '@bid-king/shared'`。
- **禁止深路径 import**：`@bid-king/shared/src/xxx` ❌。所有对外 API 必须从 `index.ts` 统一导出。
- **相对导入必须带 `.ts` 后缀**（Cocos Creator 3.8 SystemJS 硬性要求）：
  - ✅ `import { X } from './foo.ts'`
  - ✅ `export * from './types/item.ts'`
  - ❌ `import { X } from './foo'`（会被 Cocos 拒绝："Did you forget the extension?"）
  - TS 层已通过 `tsconfig.base.json` 开启 `allowImportingTsExtensions: true` 支持此写法。
  - 跨包 import（`from '@bid-king/xxx'`）不需要加后缀，只有相对路径才要。

## 七、分支与工作流

### 7.1 分支模型（轻量 Git Flow）

| 分支                      | 用途         | 合并来源                       | 受保护 |
| ------------------------- | ------------ | ------------------------------ | ------ |
| `main`                    | 生产可发布   | `dev` via PR + tag             | ✅     |
| `dev`                     | 日常集成     | `feature/*`、`fix/*`           | ✅     |
| `feature/<ticket>-<desc>` | 新功能       | 从 `dev`                       | ❌     |
| `fix/<ticket>-<desc>`     | Bug 修复     | 从 `dev`（紧急从 `main`）      | ❌     |
| `hotfix/<desc>`           | 线上紧急修复 | 从 `main`，合回 `main` + `dev` | ❌     |
| `release/<version>`       | 发版前冻结   | 从 `dev`                       | ❌     |

**1-2 人团队简化规则**：

- 可不做 `release/*`，直接 `dev → main` + tag。
- 所有分支**必须通过 PR 合入**，不允许直 push `main`/`dev`。
- PR **至少自审一遍**（1 人时），2 人时**互审**。

### 7.2 分支命名

```
feature/P2-13-network-manager
fix/P3-15-economy-rebate-calc
hotfix/room-crash-on-reveal
```

前缀 + 排期任务 ID + 短语描述（kebab-case）。

### 7.3 合并策略

- **Squash merge**（默认）：PR 合入 `dev` 时压成一个 commit，commit message 用 PR 标题。
- `main` ← `dev` 用 **merge commit**，保留 release 历史。
- **禁止 force push** `main`/`dev`。

## 八、Commit 规范（Conventional Commits）

### 8.1 格式

```
<type>(<scope>): <subject>

<body>

<footer>
```

### 8.2 Type

| type       | 含义               |
| ---------- | ------------------ |
| `feat`     | 新功能             |
| `fix`      | Bug 修复           |
| `refactor` | 重构（无功能变化） |
| `perf`     | 性能优化           |
| `docs`     | 文档               |
| `style`    | 格式（不改逻辑）   |
| `test`     | 测试               |
| `build`    | 构建/依赖          |
| `ci`       | CI 配置            |
| `chore`    | 杂项               |
| `revert`   | 回滚               |

### 8.3 Scope

按包或模块：`shared` / `client` / `server` / `room` / `economy` / `ci` / `deps` / `docs`。

### 8.4 Subject

- 英文小写开头，不超过 50 字（中文可用，长度等价）。
- 祈使语气："add bidding panel"，不是 "added"。
- 结尾不加句号。

### 8.5 示例

```
feat(server): add sealed bid validation in BidKingRoom

- validate bid amount range against player balance
- reject bid after phase deadline
- emit bid:accepted event without revealing amount

Refs: P2-04
```

```
fix(client): prevent double-click on bid submit

Closes: #42
```

### 8.6 强制校验

用 **commitlint + husky** 本地钩子 + CI 拦截：

```
- pre-commit: lint-staged（只 lint 变更文件）
- commit-msg: commitlint 校验格式
- pre-push: pnpm typecheck（快速 tsc --noEmit）
```

## 十、网络协议与 Schema 规范（核心）

这是 Monorepo 价值最大的地方，**客户端和服务端必须共享同一份类型定义**。

### 10.1 消息命名

- **客户端 → 服务端**：动词型，如 `bid:submit`、`skill:use`、`room:ready`。
- **服务端 → 客户端**：事件型，如 `bid:accepted`、`phase:changed`、`reveal:finished`。
- **全部小写 + 冒号分隔**，在 `shared/src/messages/events.ts` 集中定义：

```ts
export const ClientEvent = {
  BID_SUBMIT: 'bid:submit',
  SKILL_USE: 'skill:use',
  ROOM_READY: 'room:ready',
} as const;

export const ServerEvent = {
  BID_ACCEPTED: 'bid:accepted',
  PHASE_CHANGED: 'phase:changed',
  REVEAL_FINISHED: 'reveal:finished',
  ERROR: 'error',
} as const;
```

### 10.2 消息体类型

**每一个消息都必须有显式的 TS 类型**，双端共用：

```ts
// shared/src/messages/bid.ts
export interface BidSubmitPayload {
  containerId: string;
  amount: number;
}

export interface BidAcceptedPayload {
  playerId: string;
  // ⚠️ 绝不包含 amount，暗标金额不广播
}
```

### 10.3 Colyseus Schema

- 所有 Schema 类放 `shared/src/protocol/`。
- 字段顺序一旦发布不可调换（Colyseus 用字段顺序做序列化）。
- **敏感字段**（如其他人的出价、技能私有信息）**不放 Schema**，改用定向消息下发。

### 10.4 协议变更流程

1. 先在 `shared` 改类型 / Schema。
2. 服务端、客户端同步改实现。
3. PR 标题加 `[BREAKING]` 标识。
4. Squash merge 后客户端发新版，服务端做**向前兼容**（至少兼容 1 个小版本）。

### 10.5 错误码统一

`shared/src/constants/errorCodes.ts`：

```ts
export const ErrorCode = {
  OK: 0,
  AUTH_REQUIRED: 1001,
  BID_OUT_OF_RANGE: 2001,
  BID_TOO_LATE: 2002,
  INSUFFICIENT_BALANCE: 2003,
  SKILL_ON_COOLDOWN: 3001,
  // 1xxx 鉴权, 2xxx 出价, 3xxx 技能, 4xxx 匹配, 9xxx 系统
} as const;
```

## 十一、服务端规范

### 11.1 分层

```
routes / Room (接入层)
  ↓ 只做参数校验、鉴权
services (业务层)
  ↓ 业务逻辑、事务
repositories (数据层)
  ↓ 只做 CRUD
db / cache
```

**禁止**：Room 里直接 `User.findOne()`；必须经 service → repository。

### 11.2 异步

- **一律 async/await**，禁止 `.then()` 链。
- **未处理的 Promise 必须用 `void` 显式标注**：
  ```ts
  void doBackgroundJob(); // 明确告知"不等它"
  ```
- **错误处理**：所有 async 函数要么自己 try/catch，要么向上抛。顶层（Room handler / route）必须兜底 catch。

### 11.3 日志

- 用 **pino**（JSON 日志），区分级别 `fatal/error/warn/info/debug`。
- 关键事件必打：登录、开局、出价（脱敏）、结算、异常。
- **禁止 `console.log`**（ESLint 拦截）。
- 每条日志带 `roomId` / `userId` 上下文。

### 11.4 配置

- `dotenv` 加 `.env.example` 模板；**`.env` 不入库**。
- 配置集中 `server/src/config/index.ts`，启动时校验必填项（用 `zod` 验证）。
- 敏感配置（DB 密码、JWT secret）**绝不硬编码**。

### 11.5 安全底线

- **客户端输入必须校验**（zod / 自写 guard），服务端不信任任何客户端数据。
- **暗标金额**：只在 Room 内存，绝不广播。
- **技能私有信息**：按 `playerId` 定向下发，不放公共 Schema。
- **防重放**：关键消息带 seq，服务端去重。
- **频控**：出价接口 1 秒 1 次，登录接口 10 秒 3 次。
- **JWT**：access token 2h + refresh token 7d，黑名单放 Redis。

## 十二、客户端规范（Cocos Creator）

### 12.1 场景与预制体

- **一个功能一个 Prefab**（登录、大厅、房间、结算）。
- **Scene 只做组合**，不写业务逻辑。
- 业务逻辑放 TS 组件，**一个组件只做一件事**，超过 300 行考虑拆分。

### 12.2 组件脚本

```ts
@ccclass('BiddingPanel')
export class BiddingPanel extends Component {
  @property(Label)
  private bidLabel: Label = null!; // 编辑器拖拽的用 null! 明确声明

  protected onLoad() {
    /* 初始化 */
  }
  protected onDestroy() {
    /* 清理 */
  }

  // 对外 API
  public show(): void {
    /* ... */
  }

  // 私有辅助
  private updateUI(): void {
    /* ... */
  }
}
```

- **必须解绑事件**：`onLoad` 注册的，`onDestroy` 一定要解。
- **禁止在 `update` 里分配对象**（GC 压力）。

### 12.3 网络层

- **所有网络调用走 `NetworkManager` 单例**，组件不直接操作 Colyseus Room。
- **状态变更通过事件总线/响应式订阅**，组件只负责渲染。

### 12.4 资源

- 资源用 **Asset Bundle** 分包，主包 ≤ 4MB（小游戏硬限制）。
- **禁止动态拼接 `cc.resources.load` 字符串路径**（容易打包丢失）；统一常量管理。
- 图集图片命名 `snake_case`，PSD/源文件放 `tools/art/` 不入 assets。

### 12.5 平台差异

```ts
// 用 Cocos 的 SYS_CONFIG 判断平台
if (sys.platform === sys.Platform.WECHAT_GAME) {
  // 小游戏特殊逻辑
}
```

- 平台差异代码**收敛到 `client/assets/scripts/platform/*`**，业务层不感知。

## 十三、配置表规范

- **一切游戏数值（物品、技能、段位、掉率）走配置表**，不硬编码。
- 来源：Excel / CSV / JSON（团队选一）。
- 工具 `tools/config-gen/`：Excel → JSON → TS 常量（`shared/src/data/`）。
- **客户端、服务端必须加载同一份表**，避免双方数值不一致。
- 表字段变更必须双端同时发版。

## 十四、测试规范

### 14.1 覆盖优先级

| 类型     | 覆盖对象                                          | 工具                          | 要求               |
| -------- | ------------------------------------------------- | ----------------------------- | ------------------ |
| 单元测试 | `shared/`、`server/services/`、经济计算、技能逻辑 | Vitest                        | 核心函数必须覆盖   |
| 集成测试 | Colyseus Room 全流程                              | Colyseus `boardwalk` + Vitest | 关键流程覆盖       |
| 手工测试 | 客户端 UI / 动效                                  | 真机                          | P1/P2 每里程碑一次 |

### 14.2 单测写法

- 文件同目录 `*.test.ts`。
- 命名 `describe('UserService', () => { it('should ...') })`。
- **一个 test 一个断言概念**，别塞太多。
- **禁止依赖真实 DB**：用内存 mock（`mongodb-memory-server`）或 stub。

### 14.3 CI 运行

- `pnpm test` 必须在 CI 跑通，失败阻断合并。
- 覆盖率不强制，但关键模块（经济、结算、防作弊）鼓励 ≥ 70%。

## 十五、安全与敏感信息

- **密钥类文件永不入库**：`.env`、`*.p8`、`*.keystore`、`serviceAccount*.json`。

- 生产配置走环境变量或腾讯云密钥管理（KMS）。

## 十六、依赖管理

- **新增依赖前问自己三个问题**：
  1. 标准库能做到吗？
  2. 已装的包能做到吗？
  3. 这个依赖最近一年有更新吗？
- **客户端依赖慎之又慎**（影响包体）：每新增一个 npm 包，查 bundle 增量。
- **禁止的包**（历史坑）：`moment`（用 dayjs）、`request`（停维护）、`node-fetch@2`（ESM 问题）。
- **安全**：每月跑一次 `pnpm audit`，高危漏洞当周修。

## 十八、性能与包体

### 客户端

- **主包 ≤ 4MB**（小游戏硬限）；违规 PR 直接打回。
- **单张图 ≤ 500KB**，超过必须切图或走远程加载。
- **音效必须压缩**（mp3 96kbps 单声道 或 m4a）。
- **每周跑一次 `cocos build --analyze`** 看包体增量。

### 服务端

- **单房间内存 < 5MB**，100 房间机器内存 < 2GB。
- **消息频率**：每房间 ≤ 10 msg/s。
- **DB 查询**：Room 热路径上禁止 DB 查询，所有状态走 Schema + Redis。

## 十九、紧急响应与回滚

- **线上 Bug 分级**：
  - P0（所有玩家不可玩）：30 分钟内热修或回滚。
  - P1（部分功能不可用）：2 小时内。
  - P2（体验问题）：下个版本修。
- **回滚流程**：`hotfix/*` 分支 → 最小改动 → 直上 `main` → 灰度 10% → 全量。
- **线上事故必须有事后复盘**（`docs/incidents/*.md`），写清原因、影响、改进项。

## 二十、常见 FAQ

**Q1：可以在客户端直接引入 mongodb driver 吗？**  
不行。客户端不接触数据库，一切数据走服务端协议。

**Q2：临时想打印调试怎么办？**  
用封装的 `logger.debug(...)`，或 `// TODO: remove before merge` 标记自己清理。禁止提交 `console.log`。

**Q3：发现老代码不规范，是否要边做边重构？**  
**不要**。单独开 `refactor/*` 分支，PR 明确只做重构，不夹带功能。

**Q4：配置表新增字段，客户端没来得及适配怎么办？**  
服务端做向前兼容（默认值/可选字段），客户端下版本补齐。**绝不破坏性变更**。

**Q5：1 人独立开发也要 PR 吗？**  
要。self-approve 也要走 PR，目的是**留下变更记录和自审时间**。
