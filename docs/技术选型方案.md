# 《竞拍之王》手游复刻 - 技术选型方案

> 制定时间：2026 年 4 月  
> 项目定位：完整复刻《竞拍之王》，覆盖 iOS + Android + 微信小游戏三端  
> 团队规模：1-2 人独立开发，Web/前端背景  
> 核心诉求：开发速度快、一套代码跨平台、UI/动效表现力强

---

## 一、选型结论速览

| 层次           | 推荐方案                                              | 关键理由                                                           |
| -------------- | ----------------------------------------------------- | ------------------------------------------------------------------ |
| **客户端引擎** | **Cocos Creator 3.x**（首选）                         | 原生支持 iOS/Android/微信小游戏三端，TypeScript 开发，前端无缝衔接 |
| **UI/动效**    | Cocos 内建 UI + Spine/DragonBones 骨骼动画 + 自研粒子 | 开箱读条、抽奖式反馈表现力足够                                     |
| **服务端语言** | **Node.js (TypeScript)**                              | 与客户端同语言、同类型定义，1-2 人团队效率最优                     |
| **网络框架**   | **Colyseus**（多房间实时同步框架）                    | 专为 4-N 人房间制游戏设计，房间 / 状态同步 / 匹配开箱即用          |
| **传输协议**   | **WebSocket（小游戏原生支持） + 可选 UDP 网关**       | 暗标游戏非动作帧同步，WS 完全够用                                  |
| **数据库**     | **MongoDB + Redis**                                   | Mongo 存账号/局数/藏品，Redis 做匹配队列/房间态/排行榜             |
| **账号系统**   | 微信登录（小游戏）+ Apple/Google（App 端）+ 游客      | 三端统一 UID 绑定                                                  |
| **部署**       | 腾讯云 CVM / 轻量应用服务器 + 容器化（Docker）        | 国内网络质量好、与微信生态近                                       |
| **CI/CD**      | GitHub Actions / 云效 + fastlane（iOS 打包）          | 独立开发者友好                                                     |
| **监控与日志** | 腾讯云 CLS + Sentry                                   | 客户端崩溃 + 服务端日志一站式                                      |

**一句话总结**：Cocos Creator（TS）+ Colyseus（Node/TS）+ MongoDB/Redis，全栈 TypeScript，一套语言、一套类型、一套协议吃透三端。

## 二、客户端引擎选型分析

### 候选对比

| 引擎                                         | 三端支持                                                   | 语言          | 学习成本（前端背景）      | UI/动效                   | 生态               | 结论                                                        |
| -------------------------------------------- | ---------------------------------------------------------- | ------------- | ------------------------- | ------------------------- | ------------------ | ----------------------------------------------------------- |
| **Cocos Creator 3.x**                        | iOS ✅ Android ✅ 微信小游戏 ✅（官方首发支持）            | TypeScript    | ⭐⭐⭐⭐⭐ 极低           | 成熟 UI 系统 + Spine/粒子 | 国内最大小游戏生态 | ✅ **推荐**                                                 |
| Unity                                        | iOS ✅ Android ✅ 小游戏 △（需 Tuanjie / WX 插件，坑较多） | C#            | ⭐⭐ 中等，需学 C# + 引擎 | 表现力最强                | 全球最大           | 小游戏端体验差，团队 1-2 人且 Web 背景不划算                |
| Unreal                                       | 同上                                                       | C++/Blueprint | ⭐ 高                     | 过剩                      | 重度项目           | **不推荐**，杀鸡用牛刀                                      |
| Godot                                        | iOS/Android ✅ 小游戏 ❌                                   | GDScript/C#   | ⭐⭐⭐                    | 一般                      | 偏小               | 小游戏不支持，**排除**                                      |
| LayaAir                                      | 三端 ✅                                                    | TypeScript    | ⭐⭐⭐⭐ 低               | 一般                      | 国内中等           | 可备选，但生态弱于 Cocos                                    |
| **Laya + Cocos 之外：纯 Web + Taro/uni-app** | 三端 ✅                                                    | TS/Vue        | ⭐⭐⭐⭐⭐                | ⚠️ 复杂动效吃力           | —                  | 只适合 UI 重、动效轻项目，本项目**开箱读条/粒子**需求会吃力 |

### 为什么是 Cocos Creator

1. **微信小游戏是一等公民**：官方适配成熟，包体、启动、分包、云开发对接都有现成方案。而 Unity 发小游戏目前还需 Tuanjie/第三方插件，独立开发者踩坑成本高。
2. **TypeScript 原生**：你的前端背景无缝迁移，ESM 模块、装饰器、Promise/async 都在。
3. **包体控制**：微信小游戏主包 **≤ 4MB**、总包 ≤ 30MB（2024 年后放宽，但仍需严控）。Cocos 对分包、资源按需加载支持完善。
4. **开箱读条 / 抽奖式表现力**：Cocos 的 Tween + 粒子 + Spine 足以做到三角洲级别的刮奖感。
5. **社区资源**：国内竞品大量使用，遇到问题能搜到中文答案。

### 版本建议

- **Cocos Creator 3.8 LTS**（或当前 LTS）
- 渲染：2D 为主（桌面竞拍场景可 2.5D 伪 3D）
- 小游戏端额外启用 **WXMiniGame 专属构建配置**

## 三、服务端选型分析

### 为什么是 Node.js + Colyseus

本作是 **4 人房间制 + 轻状态同步 + 暗标为主** 的游戏，不是 MOBA/FPS 级别的帧同步，对服务端性能要求并不极端。因此选型优先级是：**开发效率 > 性能极限**。

| 候选                        | 语言 | 房间同步框架               | 上手       | 适配度            | 结论                     |
| --------------------------- | ---- | -------------------------- | ---------- | ----------------- | ------------------------ |
| **Node.js + Colyseus**      | TS   | Colyseus（专为房间制游戏） | ⭐⭐⭐⭐⭐ | ✅ 与客户端同语言 | ✅ **推荐**              |
| Node.js + Socket.IO（自研） | TS   | 自己撸状态同步             | ⭐⭐⭐⭐   | 灵活但重复造轮子  | 备选                     |
| Go + 自研                   | Go   | 自研                       | ⭐⭐       | 性能强            | 1-2 人团队学习成本不划算 |
| C# + Mirror/MagicOnion      | C#   | Unity 强绑                 | ⭐⭐⭐     | 若选 Unity 才考虑 | 排除                     |
| Pomelo（网易开源）          | Node | 停维护多年                 | ⭐⭐       | —                 | **不推荐**               |

### Colyseus 为什么适合本项目

- **房间（Room）模型**：天然匹配 4 人局，每局一个 Room 实例。
- **@Schema 状态同步**：服务端声明权威状态，客户端自动 diff 同步，**暗标这种"服务端扣留信息"场景**极好处理——只同步"已出价"状态，不同步具体数字。
- **Matchmaker**：自带匹配、排队、房间列表、好友局邀请。
- **TypeScript 原生**：和客户端共享类型定义（协议体），几乎零心智负担。
- **水平扩展**：官方 Proxy/Presence 方案支持多进程、多机。

### 暗标的服务端权威设计（关键）

这是**整个项目最核心的安全点**：

```
出价流程：
客户端 → 加密传输 bidAmount → 服务端 Room 内存中暂存
       → 服务端不广播具体金额，只广播 "玩家 X 已出价" 事件
       → 所有玩家出价完成/倒计时结束 → 服务端一次性揭晓最高价
       → 客户端渲染结果

必须：
- 出价金额永远不经客户端广播
- 客户端只持有自己的出价
- 防作弊：金额范围校验、频次限流、余额二次核对
```

## 四、数据存储选型

| 用途                           | 选型                        | 理由                                                  |
| ------------------------------ | --------------------------- | ----------------------------------------------------- |
| 玩家账号、藏品、局数流水       | **MongoDB**                 | 文档型适合不规则藏品数据、扩展字段方便、Node 生态成熟 |
| 匹配队列、房间状态缓存、排行榜 | **Redis**                   | ZSet 做排位天然适配、Pub/Sub 做跨进程消息             |
| 资源/静态文件                  | **腾讯云 COS / 阿里云 OSS** | 小游戏远程资源加载                                    |
| 日志                           | **腾讯云 CLS** 或自建 ELK   | 独立开发者优先选云服务                                |

**不建议用关系型数据库（MySQL/PG）起步**：藏品、技能、局数流水字段变化频繁，Mongo 更灵活；1-2 人团队也没精力维护复杂 schema 迁移。

## 五、账号与登录

三端要打通 UID：

| 平台       | 登录方式                       | 实现                       |
| ---------- | ------------------------------ | -------------------------- |
| 微信小游戏 | `wx.login` + code2session      | 服务端换 openid/unionid    |
| iOS        | Sign in with Apple（上架强制） | 服务端验证 identityToken   |
| Android    | Google Sign-In / 手机号        |                            |
| 三端通用   | 游客模式（设备 ID）            | 可后续绑定任一上述账号升级 |

**UID 方案**：服务端自己发全局 UID，不直接用 openid/AppleID，便于多端绑定。

## 六、核心技术难点与方案

### 1. 暗标机制（最核心）

- **权威服务端**：所有出价金额仅在服务端 Room 内存，完成回合后一次性揭晓。
- **可选加密**：客户端到服务端传输可加一层 AES 简单加密（防抓包分析他人节奏），但不是必须——TLS 已足够。
- **倒计时同步**：服务端发 `deadline` 时间戳，客户端自行倒计时，避免依赖客户端 tick。

### 2. 开箱读条 / 抽奖式反馈

- **预计算结果**：仓库内容物在开局时服务端就已随机生成并落库（保证不可篡改）。
- **客户端只演出**：读条、粒子、抖屏都是本地演出，不影响结果。
- **Spine 骨骼动画 + Cocos 粒子** 足以做出刮奖感。

### 3. 干员技能（信息差）

- **严格服务端下发**：洞察类/嗅探类技能的"信息"服务端根据玩家身份**定向推送**，不能广播后让客户端自己过滤。
- 数据结构示例：
  ```ts
  // 服务端 Schema
  class ContainerState extends Schema {
    @type('string') id: string;
    @type('number') publicItemCount: number; // 公开的大致数
    // 私有字段仅对特定玩家下发
    privateInfo: Map<playerId, PrivateInfo>;
  }
  ```

### 4. 匹配与房间

- Colyseus Matchmaker 直接用。
- 独立开发者前期可单进程、单机、房间常驻内存；玩家量上来后再 Redis Presence 分布式。

### 5. 微信小游戏特有约束

- **主包 ≤ 4MB，总包 ≤ 30MB**：音效、Spine 骨骼必须**远程加载 + 分包**。
- **iOS 小游戏禁止动态下载 JS 代码**：Cocos 脚本必须整包内，只远程资源。
- **性能**：低端安卓微信内存 <1GB 场景要做降级方案。
- **登录态**：`wx.login` 的 code 只能用一次，服务端必须缓存 session_key。
- **支付**：小游戏虚拟支付政策严格，国内个人号无法开通虚拟支付，需**企业主体 + 软著 + 版号**（变现建议放一放，先验证玩法）。

### 6. 防作弊底线

- 客户端是**纯演示层**，所有判定服务端做。
- 出价、余额、技能使用、结算全部服务端校验。
- Cocos 代码混淆 + 微信小游戏分包加密开启。

## 七、项目结构建议（Monorepo）

强烈建议 **pnpm + Turborepo** 做 Monorepo，共享协议定义：

```
bid-king/
├── packages/
│   ├── shared/                 # 协议、常量、类型定义（客户端/服务端共享）
│   │   ├── protocol/           # Colyseus Schema
│   │   ├── constants/          # 技能 ID、物品 ID、错误码
│   │   └── types/
│   ├── client/                 # Cocos Creator 项目
│   └── server/                 # Node.js + Colyseus 服务端
├── tools/
│   ├── build-scripts/          # 小游戏打包、iOS/Android 打包
│   └── item-editor/            # 藏品/仓库配置表工具（可选）
├── docs/
└── package.json
```

全栈同一份 TypeScript 类型，改协议一处即全端飘红，**1-2 人团队效率最大化**。

## 十、风险提示

1. **版号问题**：国内发行商用小游戏端如果不涉及虚拟支付，个人号可上线；一旦要接支付，**必须版号 + 企业主体**，时间成本不可控。可考虑**先做海外小游戏/TikTok 小游戏或只做纯免费版**。
2. **主播生态**：原版靠小象大鹅 MCN 拉动，个人项目没有这种资源，**必须在设计阶段就做好切片传播钩子**（15 秒爆点、自动生成战报海报、一键分享）。
3. **经济崩塌**：原版 Steam 好评率只有 49%，核心就是经济模型被"恶意抬价"打崩。复刻版**必须在第一天就加入制衡机制**（保底返还、恶意行为惩罚、段位隔离）。
4. **AI 美术争议**：可以用 AI 辅助，但**关键角色立绘、Logo、核心 UI** 建议请画师润色，否则直接复制原版风格风险大。

## 十一、备选方案（如果 Cocos 不合适）

如果你更偏好 Vue/React 工具链：

- **备选 A：Laya + TypeScript**：同样三端通吃，但生态稍弱。
- **备选 B：Unity + 微信小游戏插件**：若之后想扩展到 Steam（3D 化），长期潜力更大，但短期 1-2 人团队压力大。
- **备选 C：Taro + PixiJS/Three.js**：纯 Web 栈，开发最快，但微信小游戏端性能 / 复杂动效会明显吃力，**不推荐**做这种博弈类游戏。
